Lorsqu'un travail doit être chiffré avant d'être exécuté, les fournisseurs soumettent des **propositions** (soumissions) contre le bon de travail. Via l'API Acheteur, les propositions sont **en lecture seule** : vous les listez, inspectez les postes et les réconciliez avec les factures. Approuver ou refuser une proposition se fait dans l'application OpenWrench.

Tous les exemples supposent :

```bash
export BASE="https://api.useopenwrench.com/api/external"
export KEY="<your-api-key>"
export SECRET="<shared-secret>"
```

## Statuts de proposition

| Statut | Signification |
| --- | --- |
| `draft` | Le fournisseur est encore en train de modifier. Jamais visible pour les acheteurs. |
| `pending` | Soumise, en attente de votre décision. |
| `awarded` | Approuvée; le travail se poursuit au prix soumis. |
| `declined` | Refusée (les raisons du refus sont dans `declineNotes`). |

Les statuts sont conservés en minuscules.

## Lire les propositions

```bash
# Propositions en attente à l'échelle de l'entreprise, les plus récentes en premier
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/buyer/quote/proposals?status=pending&sort_by=createdAt&order=desc&limit=25"

# Propositions sur un bon de travail
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/buyer/quote/proposals?workOrderId=9001"

# Une proposition
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" "$BASE/v1/buyer/quote/proposals/3320"
```

Règles de portée à connaître :

- Les brouillons non soumis des fournisseurs sont toujours exclus des listes.
- Si le contact associé à votre clé d'API est restreint par emplacement, vous ne voyez que les propositions pour les emplacements accessibles. Un contact avec un ensemble d'accès vide obtient une page vide, pas une erreur.
- La lecture unique renvoie `404` pour les propositions supprimées de façon logique, les brouillons et les propositions hors de votre portée d'emplacement. Traitez `404` comme « non visible pour vous », pas nécessairement « n'existe pas ».

### Référence des filtres

La liste prend `offset`, `limit` (par défaut 10, maximum 25), `sort_by` et `order`, en plus des filtres ci-dessous. Les filtres se combinent avec ET, et se combinent toujours avec la portée de locataire et d'emplacement de votre clé. Il n'y a pas d'endpoint de comptage : le `count` de la réponse de liste est le nombre total de correspondances, alors demandez `limit=1` lorsque vous n'avez besoin que du nombre.

```bash
# Propositions octroyées de deux fournisseurs, octroyées en août
curl -G "$BASE/v1/buyer/quote/proposals" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  --data-urlencode "status=awarded" \
  --data-urlencode "supplierFacilityIds=88,91" \
  --data-urlencode "approvedAtStartDate=08/01/2026 00:00:00" \
  --data-urlencode "approvedAtEndDate=08/31/2026 00:00:00" \
  -d limit=25 -d sort_by=createdAt -d order=desc
```

| Filtre | Correspond à |
| --- | --- |
| `status`, `statuses` | Le statut de la proposition, en minuscules : `pending`, `awarded` ou `declined`. `statuses` prend une liste séparée par des virgules (`statuses=pending,awarded`). |
| `search` | Une partie du titre du bon de travail. Une valeur numérique correspond aussi exactement à l'id de la proposition ou à l'id du bon de travail. |
| `workOrderId` | Les propositions sur un bon de travail. |
| `locationId`, `locationIds` | Les propositions pour ces emplacements. Obtenez les ids d'emplacement avec [`GET /v1/buyer/location/locations`](/fr-CA/buyer-api/assets-and-locations#emplacements). |
| `regionIds` | Les propositions pour les bons de travail aux emplacements de ces régions. |
| `problemTypeIds` | Les propositions dont le bon de travail est de ces types de problèmes. Obtenez les ids avec [`GET /v1/buyer/work_order/problem_types`](/fr-CA/buyer-api/work-orders#types-de-problèmes). |
| `woPriorityIds` | Les propositions dont le bon de travail est à ces priorités. |
| `isCapex` | `true` retourne uniquement les propositions pour les bons de travail marqués comme dépenses en immobilisations; `false` les exclut. |
| `supplierFacilityId`, `supplierFacilityIds` | Les propositions de ces fournisseurs. Obtenez les ids d'établissement fournisseur avec [`GET /v1/buyer/supplier_facilities`](/fr-CA/buyer-api/supplier-network#votre-réseau-de-fournisseurs). |
| `createdAtStartDate`, `createdAtEndDate` | Les propositions créées dans la fenêtre. Une proposition rédigée dans l'application peut être soumise plus tard; son `submittedAt` indique quand. |
| `approvedAtStartDate`, `approvedAtEndDate` | Les propositions octroyées dans la fenêtre. |
| `workCompletedAtStartDate`, `workCompletedAtEndDate` | Les propositions dont le bon de travail a été complété dans la fenêtre. |

Règles des valeurs :

- **Tri.** `sort_by` prend en charge `createdAt`, `updatedAt`, `totalAfterTax`, `id`, `workOrderId`, `locationId`, `supplierFacilityId` et `buyerFacilityId`. Sans `sort_by`, ou avec toute autre valeur, les résultats sont triés par `id` croissant (les plus anciennes en premier). Dès que vous définissez `sort_by`, `order` est `asc` par défaut, alors envoyez `order=desc` pour obtenir les plus récentes en premier.
- **Les listes prennent des virgules, sans espaces.** Une clé au singulier (`status`) prend une seule valeur; la clé au pluriel prend une liste séparée par des virgules. Une espace après une virgule peut faire échouer la requête.
- **Les dates utilisent `MM/dd/yyyy HH:mm:ss` en UTC**, par exemple `08/01/2026 00:00:00`. L'heure est obligatoire. La borne de début est incluse à l'heure que vous envoyez; la borne de fin couvre toute la journée de fin. Une date qui ne peut pas être analysée est lue comme le 1er janvier 1970 plutôt que rejetée, alors une date de début invalide correspond à tout et une date de fin invalide ne correspond à rien.
- **Les valeurs doivent être bien formées.** Un id non numérique, ou un booléen autre que `true` ou `false`, peut faire échouer la requête avec un `500` plutôt qu'un `400`.
- **Les filtres non reconnus sont ignorés**, et la portée de locataire ne peut pas être contournée : `buyerCompanyId` est toujours défini à partir de votre clé d'API, et les brouillons sont exclus même si vous demandez `status=draft`.

## À l'intérieur d'une proposition

L'argent est réparti dans les mêmes sections que les factures : `laborLineItems`, `materialLineItems`, `travelLineItems`, `freightLineItems` et `miscLineItems`, chaque section avec son propre taux de taxe et `...TotalBeforeTax`, se totalisant à `totalBeforeTax`, `tax` et `totalAfterTax`. **Les valeurs monétaires sont sérialisées en chaînes**; analysez-les comme décimales, non comme flottants, si vous faites de l'arithmétique.

Autres champs utiles : `workOrderId`, `supplierFacilityId`, `workOrderNTEBeforeApproval` (le montant à ne pas dépasser du bon de travail au moment de la soumission), `proposalPdfLink`, `attachments`, `submittedAt` et `approvedAt`.

## Où les propositions s'inscrivent dans le flux

1. Le fournisseur soumet une proposition; le bon de travail se met généralement en pause en attente d'approbation.
2. Vos approbateurs l'accordent ou la refusent dans l'application. L'octroi relève le plafond de dépenses effectif du travail.
3. Lorsque la [facture](/fr-CA/buyer-api/invoices) finale arrive, comparez `invoiceTotalAfterTax` au `totalAfterTax` de la proposition octroyée avant d'approuver le paiement. Signalez les écarts au-delà de votre tolérance pour révision humaine.

Une boucle de sondage pratique pour un tableau de bord des achats : filtrez par `status=pending`, triez avec `sort_by=createdAt&order=desc` et paginez avec `limit=25`, en respectant la limite de débit de 10 requêtes par fenêtre de 20 secondes.
