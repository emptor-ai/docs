# Achats et inventaire avec l'API Fournisseur

> Gérez tout le cycle de vie des achats : demandes d'achat, bons de commande et postes, réceptions et retours, catalogues, niveaux de stock et webhook Order.co.

Les endpoints d'inventaire sous `/v1/supplier/inventory/` couvrent tout le cycle de vie des achats : les techniciens créent des **demandes d'achat** (PR), le service des achats les transforme en **bons de commande** (PO) auprès des fournisseurs, les marchandises arrivent sous forme de **réceptions**, et les niveaux de stock se mettent à jour par **emplacement de stock**. La même surface est reflétée pour les équipes internes des acheteurs dans l'[API Internal Teams](/partners-api/introduction).

Tous les exemples supposent :

```bash
export BASE="https://api.useopenwrench.com/api/external"
export KEY="<your-api-key>"
export SECRET="<shared-secret>"
```

## Demandes d'achat

Statuts de PR : `requested`, `denied`, `cancelled`, `approved`, `orderInProgress`, `ordered`, `partially_ordered`, `fulfilled`, `partially_fulfilled`.

```bash
# PR approuvées en attente de commande
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/supplier/inventory/purchase_requests?status=approved&limit=25"

# Une PR avec ses postes
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/supplier/inventory/purchase_requests/601"
```

Deux écritures de statut :

- `PATCH /v1/supplier/inventory/purchase_requests/{id}/cancelled` annule, et ne fonctionne que depuis un statut annulable (`requested` ou `approved`) ; tout autre statut renvoie `400`.
- `PATCH /v1/supplier/inventory/purchase_requests/{id}/{status}` définit n'importe quel statut de la liste ci-dessus. Les noms inconnus sont rejetés.

En fonctionnement normal, vous définissez rarement directement les statuts de PR : ils sont **recalculés à partir des postes** au fur et à mesure que vous les associez à des PO, et la satisfaction se produit à la complétion des bons de travail.

### Postes de PR

Les postes sont interrogés séparément, ce qui vous permet de construire une liste de travaux de commande à travers de nombreuses PR :

```bash
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/supplier/inventory/purchase_request_line_items?status=approved&partId=210"
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/supplier/inventory/purchase_request_line_items/count_by?status=approved"
```

Ces deux endpoints ne sont pas soumis à la limite de débit et utilisent les valeurs par défaut de pagination internes plutôt que le plafond externe 10/25.

Le pont entre les PR et les PO est `PATCH /v1/supplier/inventory/purchase_request_line_items/associate_po_line_item/{ids}/{poLineItem}` : il prend des identifiants de postes de PR séparés par des virgules, définit chacun à `orderInProgress` avec son `associatedPurchaseOrderLineItemId`, et recalcule le statut de chaque PR parente. Les identifiants pour lesquels vous n'avez pas la permission sont silencieusement supprimés, comparez donc la liste retournée avec ce que vous avez envoyé.

## Bons de commande

Statuts de PO : `new`, `ordered`, `received`, `partially_received`, `cancelled`, `closed`.

### Créer

`POST /v1/supplier/inventory/purchase_orders` requiert `status` (généralement `new`), `partEquipmentVendorId`, `currencyId` et `createdByEmail`. `totalCost` est également requis, sauf si les paramètres d'inventaire de votre entreprise indiquent que le coût du PO n'est pas obligatoire.

```bash
curl -X POST "$BASE/v1/supplier/inventory/purchase_orders" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "status": "new",
    "partEquipmentVendorId": 44,
    "currencyId": "USD",
    "createdByEmail": "purchasing@supplier.com",
    "stockLocationId": 7,
    "totalBeforeTax": 620.00,
    "tax": 52.70,
    "totalCost": 672.70,
    "incomingLineItems": [
      {
        "isEquipmentLine": false,
        "partId": 210,
        "partQuantity": 2,
        "partUomId": 1,
        "partCost": 310.00,
        "partCurrencyId": "USD",
        "prLineItemIds": [8801, 8802]
      }
    ]
  }'
```

Les postes distinguent les lignes de pièces des lignes d'équipement via `isEquipmentLine` ; les lignes de pièces portent `partId`/`partQuantity`/`partUomId`/`partCost`/`partCurrencyId`, les lignes d'équipement les équivalents `equipment*`. `prLineItemIds` relie la ligne aux demandes d'achat qu'elle satisfait. Passer un `id` de premier niveau met à jour un PO existant.

### Remplacer les postes en masse

`POST /v1/supplier/inventory/purchase_order_line_items/bulk` prend un **tableau JSON** de payloads de postes et a des sémantiques de remplacement :

<Warning>
Tous les postes **non reçus** du bon de commande cible sont d'abord supprimés, puis les articles soumis sont créés. Envoyez toujours l'ensemble complet des lignes ouvertes prévues, jamais seulement le delta. Les articles pour lesquels vous n'avez pas la permission d'écriture sont silencieusement ignorés.
</Warning>

`supplierFacilityId` et `supplierCompanyId` sur chaque article sont écrasés depuis votre clé, les listes d'identifiants de pièces/équipements/PR du PO sont recalculées, et la notification de bon de commande est renvoyée. Non soumis à la limite de débit.

### Marquer comme commandé

`PATCH /v1/supplier/inventory/purchase_orders/{id}/ordered` définit le statut à `ordered` et envoie la commande par courriel au fournisseur.

<Note>
La réponse de succès est une enveloppe de chaîne (`"type": "Email"`, `"data": "Email has been sent"`), **et non** le bon de commande. Récupérez à nouveau le PO si vous avez besoin de son état mis à jour.
</Note>

`PATCH /v1/supplier/inventory/purchase_orders/{id}/cancel` annule et retourne le PO mis à jour.

## Réceptions et retours

La réception est un `PUT` associé au poste du PO :

```bash
curl -X PUT "$BASE/v1/supplier/inventory/purchase_order_receipts" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "receiptNumber": "RCPT-1042",
    "purchaseOrderId": 350,
    "purchaseOrderLineItemId": 9902,
    "receivedQuantity": 2,
    "pricePerQuantity": 310.00,
    "updatedBy": "warehouse@supplier.com",
    "supplierFacilityId": 12
  }'
```

Requis : `receiptNumber`, `purchaseOrderId`, `purchaseOrderLineItemId`, `receivedQuantity`, `updatedBy`, `supplierFacilityId`. Règles :

- `receivedQuantity` doit être non nul. **Une quantité négative enregistre un retour.**
- La réception met à jour les quantités et coûts reçus du poste du PO et les enregistrements de stock à l'emplacement de stock de destination ; le statut du PO se cumule à `partially_received`/`received` en conséquence.
- Pour l'équipement sérialisé, `equipmentPerStockLocationReceiptValues` (ou `assetReceiptValues`/`receiptValuesWithoutId`) porte une entrée `{ serialNumber, assetNumber }` par unité. La longueur de la liste doit être égale à `receivedQuantity`, ces tableaux ne sont pas autorisés sur les retours, et les numéros de série ou d'actif déjà utilisés sont rejetés.
- Les métadonnées de facture fournisseur (`invoiceNumber`, `invoiceCurrency`, `invoiceTotal`, `exchangeRate`, `invoiceTotalPostExchange`) peuvent être enregistrées sur la réception.

Relisez-en une avec `GET /v1/supplier/inventory/purchase_order_receipts/{id}`.

## Catalogue : pièces, équipements, fournisseurs et stock

Données de référence en lecture seule, toutes avec pagination standard et filtres par champ :

| Endpoint | Contenu |
| --- | --- |
| `GET /v1/supplier/inventory/parts` (+`/{id}`) | Votre catalogue de pièces. |
| `GET /v1/supplier/inventory/equipments` (+`/{id}`) | Types d'équipement (modèles). |
| `GET /v1/supplier/inventory/part_equipment_vendors` (+`/{id}`) | Fournisseurs auprès desquels vous commandez. |
| `GET /v1/supplier/inventory/parts_per_stock_locations` (+`/{id}`) | Inventaire des pièces par emplacement de stock : quantités et emplacements de bac. |
| `GET /v1/supplier/inventory/equipment_per_stock_locations` (+`/{id}`) | Unités d'équipement sérialisées détenues aux emplacements de stock. |

`parts_per_stock_locations?partId=210` répond à « où avons-nous cette pièce et en quelle quantité » ; filtrez par `stockLocationId` pour la liste complète de stock d'un emplacement.

## Webhook Order.co

`POST /v1/supplier/inventory/webhook/purchase_order` est un webhook **entrant** pour les systèmes d'achat tiers, actuellement Order.co, et uniquement pour les entreprises fournisseurs qui y sont enregistrées (les autres reçoivent `400`). Le payload porte `order_id` (l'identifiant tiers), `purchase_order_number` (l'identifiant OpenWrench du PO en tant que chaîne), un `status` et un objet `message` spécifique au statut. Effets par statut :

- `approved` / `error` — ajoute une note au PO.
- `rejected` — annule le PO.
- `completed` — marque le PO comme commandé.
- `shipping_update` — ajoute une note d'expédition ; lorsque `message.shipment_delivery_date` est présent, crée automatiquement des réceptions pour tous les postes non reçus.

Chaque requête et réponse est auditée, et la forme de la réponse varie selon la branche.

## Le flux complet en un coup d'œil

1. Listez les postes de PR `approved` pour construire la liste de travaux de commande.
2. Créez le PO avec `incomingLineItems` référençant `prLineItemIds` (ou associez explicitement les postes de PR par la suite).
3. Marquez le PO `ordered` (le fournisseur reçoit le courriel).
4. Recevez les livraisons avec des réceptions ; enregistrez les retours en tant que quantités négatives ; les unités sérialisées reçoivent des numéros de série et d'actif par unité.
5. Les statuts de PR avancent automatiquement (`orderInProgress` → `ordered` → `fulfilled`) au fur et à mesure que les postes s'associent et que les bons de travail se complètent.
