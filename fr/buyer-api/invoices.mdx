# Cycle de vie des factures et flux de paiement dans l'API Acheteur

> Lisez, approuvez et payez les factures des fournisseurs avec l'API Acheteur OpenWrench, y compris les transitions de statut, la synchronisation avec les systèmes de comptabilité fournisseurs, les exports aplatis et les mises à jour groupées.

Les fournisseurs facturent les bons de travail complétés au moyen de factures. L'API Acheteur est l'endroit où votre intégration comptable les lit, les fait progresser dans le circuit d'approbation et les marque comme payées. Les factures peuvent aussi être rattachées à un projet plutôt qu'à un bon de travail. Les mêmes statuts et endpoints de paiement s'appliquent, avec les différences signalées ci-dessous.

Tous les exemples supposent :

```bash
export BASE="https://api.useopenwrench.com/api/external"
export KEY="<your-api-key>"
export SECRET="<shared-secret>"
```

## Statuts de facture

Les factures portent un `status` en minuscules :

| Statut | Signification |
| --- | --- |
| `draft` | Le fournisseur est encore en train de la modifier. **Jamais visible dans les lectures acheteur.** |
| `pending` | Publiée pour vous, en attente d'examen. |
| `approved` | Approuvée pour paiement. |
| `processing` | Dans votre exécution de paiement. |
| `paid` | Réglée. |
| `disputed` | Vous l'avez contestée (contestation soulevée dans l'application). |
| `pastdue`, `transferred`, `void` | États d'ancienneté, de transfert et d'annulation. |

Le chemin contrôlé par l'acheteur est `pending → approved → processing → paid`. Chaque transition dispose d'un endpoint dédié ; il n'existe pas de setter de statut générique.

## Lire les factures

```bash
# Factures en attente, les plus récentes en premier
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/buyer/invoice/invoices?status=pending&sort_by=createdAt&order=desc&limit=25"

# Uniquement le nombre
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/buyer/invoice/invoices/count_by?status=pending"

# Une facture
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" "$BASE/v1/buyer/invoice/invoices/7710"
```

Une facture est reliée à son `supplierFacilityId` plus **exactement un** des identifiants `workOrderId` ou `projectId` (l'autre est `null`, tout comme le `workOrder` / `project` hydraté). Les factures de bon de travail portent toujours `locationId` et `buyerFacilityId`. Les factures de projet ne les portent que si le client les a fournis, donc les deux peuvent être `null`. La facture porte la ventilation monétaire en sections (main-d'œuvre, matériel, déplacement, fret, divers), chacune avec des postes, un `taxRate` et un `totalBeforeTax`. Ces sections se cumulent dans `invoiceTotalBeforeTax`, `invoiceTax` et `invoiceTotalAfterTax`. Les valeurs monétaires sont sérialisées sous forme de chaînes. Un court résumé de la portée dérivé par IA peut apparaître dans `title`. Le PDF rendu se trouve dans `invoicePDFs` ; les fichiers d'appui se trouvent dans `attachments` (voir [Fichiers et pièces jointes](/buyer-api/files-and-attachments)).

### Lister, filtrer et compter

```bash
# Factures approuvées dans deux emplacements, publiées en août, les plus élevées en premier
curl -G "$BASE/v1/buyer/invoice/invoices" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  --data-urlencode "status=approved" \
  --data-urlencode "locationIds=1204,1310" \
  --data-urlencode "publishedAtStartDate=08/01/2026 00:00:00" \
  --data-urlencode "publishedAtEndDate=08/31/2026 00:00:00" \
  -d limit=25 -d sort_by=invoiceTotalAfterTax -d order=desc

# Uniquement les factures de projet pour ce projet
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/buyer/invoice/invoices?invoiceEntityType=project&projectId=482"
```

`GET /invoices`, `/invoices/count_by` et `/invoices/download` acceptent les mêmes filtres, décrits dans la [référence des filtres](#référence-des-filtres) ci-dessous. Les filtres se combinent avec ET, et se combinent toujours avec la restriction locataire dérivée de votre clé. Les brouillons des fournisseurs et les factures annulées ne sont jamais retournés, quel que soit le filtre.

- **Tri.** `sort_by` accepte `createdAt`, `invoiceTotalAfterTax`, `id`, `workOrderId`, `locationId`, `supplierFacilityId` et `buyerFacilityId`. Sans `sort_by`, les résultats sont triés des plus récents aux plus anciens. Dès que vous définissez `sort_by`, `order` vaut `asc` par défaut ; envoyez donc `order=desc` pour un tri décroissant. Les autres champs, comme `publishedAt`, ne sont pas triables ; filtrez plutôt sur une fenêtre de `publishedAt`.
- **Les filtres non reconnus sont ignorés.** Un paramètre de requête qui ne figure pas dans la référence des filtres est ignoré plutôt que rejeté, et la requête aboutit quand même. Avant de vous appuyer sur un nouveau filtre, comparez `count_by` avec et sans lui.

### Référence des filtres

Les clés sont sensibles à la casse. Une clé au singulier (`status`) prend une seule valeur ; la clé au pluriel (`statuses`) prend une liste séparée par des virgules et correspond à l'une quelconque des valeurs.

**Statut**

| Filtre | Correspond à |
| --- | --- |
| `status`, `statuses` | Le statut de la facture, en minuscules : `pending`, `approved`, `processing`, `paid`, `disputed`, `pastdue` ou `transferred`. Voir les [statuts de facture](#statuts-de-facture). |
| `invoiceEntityType` | `work_order` ne retourne que les factures de bon de travail ; `project` ne retourne que les [factures de projet](#factures-de-projet). Omettez-le pour obtenir les deux. |
| `workOrderDisplayStatus` | Les factures dont le bon de travail est dans ce statut d'affichage : `Pending`, `Deferred`, `Open`, `InProgress`, `OnHold`, `Completed` ou `Cancelled`. |

**Quoi et où**

| Filtre | Correspond à |
| --- | --- |
| `search` | Une partie du titre du bon de travail, ou exactement l'un des éléments suivants : identifiant du bon de travail, identifiant externe du bon de travail, numéro de facture, identifiant de facture, numéro de PO, code GL. |
| `workOrderId` | Les factures d'un bon de travail. |
| `externalWorkOrderId` | Les factures d'un bon de travail, par la référence externe que votre système enregistre sur celui-ci. |
| `projectId` | Les factures rattachées à un projet. |
| `buyerProjectId` | Les factures des bons de travail d'un projet. Un bon de travail liste ses projets dans `buyerProjectIds`. |
| `invoiceNumber` | Les factures portant ce numéro de facture fournisseur. |
| `locationId`, `locationIds` | Les factures de ces emplacements. Obtenez les identifiants d'emplacement avec [`GET /v1/buyer/location/locations`](/buyer-api/assets-and-locations#locations). |
| `regionIds` | Les factures des emplacements situés dans ces régions. |
| `assetId`, `assetIds` | Les factures dont le bon de travail porte sur ces actifs. |
| `problemTypeId`, `problemTypeIds` | Les factures dont le bon de travail a ces types de problème. Obtenez les identifiants avec [`GET /v1/buyer/work_order/problem_types`](/buyer-api/work-orders#problem-types). |
| `woPriorityIds` | Les factures dont le bon de travail a ces priorités. |
| `isPM` | `true` ne retourne que les factures des bons de travail d'entretien préventif ; `false` les exclut. |
| `isCapex` | `true` ne retourne que les factures des bons de travail marqués comme dépenses d'investissement ; `false` les exclut. |

**Qui et comptabilité**

| Filtre | Correspond à |
| --- | --- |
| `supplierFacilityId`, `supplierFacilityIds` | Les factures de ces fournisseurs. Obtenez les identifiants d'établissement fournisseur avec [`GET /v1/buyer/supplier_facilities`](/buyer-api/supplier-network#your-supplier-network). |
| `hasPONumber` | `true` retourne les factures qui portent un numéro de PO ; `false` retourne celles qui n'en ont pas. |
| `hasGLCode` | `true` retourne les factures qui portent un code GL ; `false` retourne celles qui n'en ont pas. |

**Dates**

| Filtre | Correspond à |
| --- | --- |
| `createdAtStartDate`, `createdAtEndDate` | Les factures créées dans la fenêtre. |
| `publishedAtStartDate`, `publishedAtEndDate` | Les factures que le fournisseur vous a publiées dans la fenêtre. |
| `approvedAtStartDate`, `approvedAtEndDate` | Les factures approuvées dans la fenêtre. |
| `processedAtStartDate`, `processedAtEndDate` | Les factures passées à `processing` dans la fenêtre. |
| `markedPaidAtStartDate`, `markedPaidAtEndDate` | Les factures marquées comme payées dans la fenêtre. |
| `dueAtStartDate`, `dueAtEndDate` | Les factures arrivant à échéance dans la fenêtre. |
| `workCompletedAtStartDate`, `workCompletedAtEndDate` | Les factures dont le bon de travail a été complété dans la fenêtre. |

### Règles des valeurs de filtre

- **Utilisez la clé au pluriel pour plusieurs valeurs, sans espaces.** `statuses=approved,processing` correspond à l'un ou l'autre statut. `status=approved,processing` cherche un unique statut portant ce nom littéral et ne retourne rien. Un espace après une virgule dans une liste d'identifiants peut faire échouer la requête.
- **Une valeur par clé.** Si vous répétez un paramètre, seule la première occurrence est utilisée.
- **Les dates utilisent le format `MM/dd/yyyy HH:mm:ss` en UTC**, par exemple `08/01/2026 00:00:00`. L'heure est obligatoire. La borne de début est inclusive à l'heure que vous envoyez. La borne de fin couvre toute la journée de fin : son heure est remplacée par 23:59:59. Encodez la valeur pour l'URL (`curl -G --data-urlencode` le fait pour vous). Une date qui ne s'analyse pas n'est pas rejetée. Elle est lue comme le 1er janvier 1970 : une date de début erronée correspond donc à tout, et une date de fin erronée ne correspond à rien.
- **Les booléens valent `true` ou `false`.** Toute autre valeur, ou un identifiant non numérique, peut faire échouer la requête avec un `500` plutôt qu'un `400`.
- **La restriction locataire ne peut pas être contournée.** `buyerCompanyId` est toujours défini à partir de votre clé d'API ; le passer n'a donc aucun effet.

### Export aplati

`GET /v1/buyer/invoice/invoices/download` retourne les mêmes données sous forme de lignes à plat (une ligne par facture avec les totaux dénormalisés). Cet endpoint est conçu pour l'export vers tableur et l'import dans les systèmes de comptabilité fournisseurs. Mêmes filtres que l'endpoint de liste. Sur les lignes de factures de projet, `workOrderId`, `workOrderTitle`, `problemTypeId`, `problemTypeName`, `locationId` et `locationName` sont `null` ; `projectId` est renseigné.

## Faire progresser une facture dans l'approbation

Chaque endpoint de transition ne prend que l'identifiant de la facture :

```bash
curl -X POST "$BASE/v1/buyer/invoice/status/approved" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "id": 7710 }'
```

Les quatre endpoints sont `status/pending`, `status/approved`, `status/processing` et `status/paid`. Comportement partagé :

- Chaque transition **efface l'indicateur de contestation de la facture**, puis propage un changement de statut correspondant au bon de travail associé.
- Si la correspondance du statut du bon de travail échoue, la facture est **annulée** et l'appel retourne `400`. Traitez un `400` ici comme « à récupérer et inspecter », pas comme « à réessayer ».
- Un échec de validation au niveau de la sauvegarde retourne `406`.

### Marquer comme payée par identifiant de bon de travail

Lorsque votre système comptable connaît le bon de travail mais pas l'identifiant de facture OpenWrench, bouclez la boucle avec :

```bash
curl -X POST "$BASE/v1/buyer/invoice/status/paid/by_work_order_id" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "workOrderId": "9001" }'
```

La recherche tente `workOrderId` en premier et se rabat sur `externalWorkOrderId`, toujours au sein de votre entreprise. Les factures déjà `paid` sont retournées inchangées (réessai sans risque). Les factures `approved` ou `processing` sont marquées comme payées. Une facture dans tout autre statut retourne `400` avec « Invoice not found ».

## Factures de projet

Les factures de projet sont rattachées à un projet (`projectId`) plutôt qu'à un bon de travail (`workOrderId`), et court-circuitent la partie bon de travail du pipeline. Pour une facture sans `workOrderId`, OpenWrench ignore :

- Le contrôle NTE à la création et à la mise à jour.
- La dérivation du code GL depuis le bon de travail.
- La réplique des dépenses de budget et des dépenses d'actifs.
- La synchronisation du statut du bon de travail qui s'exécute normalement à chaque transition de statut (une transition de statut sur une facture de projet n'annule jamais la facture et ne retourne jamais `400` pour une correspondance BT rompue).
- L'ajout de la page de détail du bon de travail dans l'utilitaire de PDF de facture.
- Les hiérarchies d'approbation ancrées au bon de travail ainsi que leurs notifications d'approbation / rappel / escalade.
- Le contrôle de doublons « une facture par fournisseur » au niveau du bon de travail.
- La validation sur `taxLineItems` limitée à la devise (les montants sont toujours validés comme numériques).

Les analyses de coût par emplacement et de coût par établissement n'incluent que les factures qui portent le champ correspondant. Une facture de projet créée sans `locationId` ou `buyerFacilityId` est donc exclue de ces rapports.

Le raccourci `POST status/paid/by_work_order_id` ne correspond qu'aux factures de bon de travail ; pour une facture de projet, marquez-la comme payée par `id` via `POST status/paid`.

## Utilitaires

**Ajouter la page de détail du bon de travail au PDF.** `PATCH /v1/buyer/invoice/file/invoice_pdf/add_work_order_detail_page/{invoiceId}` régénère le PDF de la facture avec la page de détail du bon de travail annexée et retourne le nouveau lien PDF (type d'enveloppe `UpdatedInvoicePdf`). Pas de corps de requête ; non soumis à la limite de débit.

**Mise à jour groupée avec filtres.** `PATCH /v1/buyer/invoice/bulk_update_with_filters` applique une mise à jour de colonnes à chaque facture correspondant à un filtre, toujours contrainte à votre entreprise. Les deux sont des mappings colonne→valeur libres :

```bash
curl -X PATCH "$BASE/v1/buyer/invoice/bulk_update_with_filters" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "filters": { "status": "approved" }, "updates": { "status": "processing" } }'
```

Il retourne le nombre de factures mises à jour. C'est un outil puissant qui contourne les effets secondaires de transition par facture, alors préférez les endpoints de statut sauf si vous avez vraiment besoin d'un balayage. Non soumis à la limite de débit.

**Publier les brouillons pour les bons de travail complétés.** `PATCH /v1/buyer/invoice/publish_draft_invoices_if_wo_complete_and_auto_publish_enabled` publie les factures fournisseur en brouillon dont le bon de travail est complet, pour les fournisseurs qui ont activé la publication automatique. Il nécessite une clé d'API acheteur **super-administrateur** et retourne `403` pour une clé normale. Prévu pour des tâches d'entretien planifiées.

## Modèle de synchronisation comptabilité fournisseurs

Une synchronisation robuste avec la comptabilité fournisseurs :

1. Interrogez `GET /invoices?status=pending` (ou par fenêtres de `publishedAt`) selon une planification.
2. Récupérez chaque facture. Pour les factures de bon de travail, comparez les totaux à la [proposition](/buyer-api/quotes-and-proposals) approuvée et au `nte` du bon de travail. Pour les factures de projet, comparez plutôt à votre budget de projet. Le contrôle NTE ne s'exécute pas côté serveur pour les factures de projet.
3. `POST status/approved`, exportez vers votre système comptable, puis `POST status/processing`.
4. Au règlement, `POST status/paid` par identifiant, ou `status/paid/by_work_order_id` avec la référence du bon de travail que votre système comptable porte.
5. Journalisez le `traceId` de l'enveloppe sur tout `400`/`406` afin que le support puisse tracer la requête exacte.
