Money flows through two objects: **proposals** (quotes the buyer approves before work proceeds) and **invoices** (the bill for completed work). Suppliers create both through this API.

<Note>
Neither endpoint is available to internal-service-team keys; quoting and invoicing are for third-party suppliers billing a buyer.
</Note>

All examples assume:

```bash
export BASE="https://api.useopenwrench.com/api/external"
export KEY="<your-api-key>"
export SECRET="<shared-secret>"
```

## Money is strings, in sections

Proposals and invoices share a line-item structure. Amounts are **strings that must parse as numbers** ("450.00", not 450.00 as a float; format with two decimals and parse as decimals). The sections are labor, material, travel, freight, and misc (proposals add incurred cost). Each section carries its own line items, tax rate, and `...TotalBeforeTax`, and the sections roll up to before-tax, tax, and after-tax totals. Travel, freight, and misc lines are simple `{ "description", "amount" }` objects.

## Proposals (quotes)

`POST /v1/supplier/quote/proposals` creates the proposal directly in **`pending`** status under your facility; there is no separate submit step. Required: `workOrderId` and `totalAfterTax`.

```bash
curl -X POST "$BASE/v1/supplier/quote/proposals" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "workOrderId": 9001,
    "scope": "Replace condenser fan motor and recharge refrigerant.",
    "laborLineItems": [ { "description": "2 techs x 3 hrs", "amount": "540.00" } ],
    "laborTotalBeforeTax": "540.00",
    "materialLineItems": [ { "description": "Fan motor", "amount": "310.00" } ],
    "materialTotalBeforeTax": "310.00",
    "totalBeforeTax": "850.00",
    "taxRate": "8.5",
    "tax": "72.25",
    "totalAfterTax": "922.25"
  }'
```

Behavior to know:

- `locationId`, `buyerFacilityId`, and `buyerCompanyId` are derived from the work order; you cannot set them.
- Unset tax fields and section totals default to `"0"`.
- `requestForProposalId` defaults to the work order's RFP when omitted.
- `proposalPdfLink`, if sent, must be a valid URL. `attachments` take `FileDetails` from the [file upload endpoint](/supplier-api/files-and-users).
- Passing an `id` updates an existing proposal.

Track the outcome by re-fetching: `status` moves from `pending` to `awarded` or `declined` (decline reasons appear in `declineNotes`). List with `GET /v1/supplier/quote/proposals` (see [filtering lists](#filtering-lists)), read one with `GET /v1/supplier/quote/proposals/{id}`.

## Invoices

### The lifecycle

Invoices start as **`draft`** (invisible to the buyer) and get **published** into `pending`. The buyer then moves them through `approved` and `processing` to `paid` (or disputes them). Your integration creates the draft and publishes it; from `pending` onward you are mostly reading status.

### Create the draft

`POST /v1/supplier/invoice/invoices` requires `workOrderId`; `locationId`, `buyerFacilityId`, `buyerCompanyId`, `spendCategoryId`, and `problemTypeId` are all derived from it.

```bash
curl -X POST "$BASE/v1/supplier/invoice/invoices" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "workOrderId": 9001,
    "invoiceNumber": "INV-2026-0451",
    "dateOfInvoice": "2026-08-21T00:00:00.000-07:00",
    "laborLineItems": [ { "description": "2 techs x 3 hrs", "amount": "540.00" } ],
    "laborTotalBeforeTax": "540.00",
    "materialLineItems": [ { "description": "Fan motor", "amount": "310.00" } ],
    "materialTotalBeforeTax": "310.00",
    "invoiceTotalBeforeTax": "850.00",
    "invoiceTaxRate": "8.5",
    "invoiceTax": "72.25",
    "invoiceTotalAfterTax": "922.25"
  }'
```

Details that bite:

- `poNumber` defaults to the work order's PO number.
- `serviceCallIds` defaults to **all** service calls on the work order when omitted or empty; set it explicitly when billing a subset of visits.
- `taxLineItems` are validated against the invoice currency's allowed tax types (currently only CAD supports them: GST/HST/PST); anything else is rejected.
- `invoicePDFLink` (a valid URL) becomes the invoice's single PDF entry if you host the PDF yourself; most integrations use the upload endpoint below instead.
- `autoPublishOnApproval` opts this invoice into auto-publishing when the work order completes.
- Saving an invoice can transition the associated work order's status per the invoice-to-work-order status mapping. A save-level validation failure returns `406`.
- Passing an `id` updates an existing invoice (drafts only, in practice; buyer-side statuses are not yours to edit).

### Upload the PDF and publish

`POST /v1/supplier/invoice/file/upload_and_publish/{invoiceId}` does both steps at once: the uploaded PDF (multipart part `file`, max 512 MB) becomes the invoice's single PDF, and the status moves to `pending`.

```bash
curl -X POST "$BASE/v1/supplier/invoice/file/upload_and_publish/7710" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -F "file=@INV-2026-0451.pdf"
```

Each precondition failing returns `400`: your facility must own the invoice, the associated work order must be in **Completed** display status, and the buyer's configuration must allow supplier invoice editing.

### Read and reconcile

`GET /v1/supplier/invoice/invoices` (filterable, see [filtering lists](#filtering-lists)) and `GET /v1/supplier/invoice/invoices/{id}`. Third-party suppliers see masked records with buyer-private fields blanked. Poll status to drive your accounts receivable (AR) ledger: `approvedAt`, `processedAt`, and `markedPaidAt` timestamp the buyer's progress.

## Filtering lists

`GET /v1/supplier/quote/proposals` and `GET /v1/supplier/invoice/invoices` take `offset`, `limit` (default 10, max 25), `sort_by`, and `order`, plus the filters below. Filters combine with AND, and always combine with your key's tenant scoping, so you only see your facility's proposals and invoices. Neither list has a count endpoint; the response's `count` is the total number of matches.

```bash
# Approved and processing invoices for one buyer, marked paid in August
curl -G "$BASE/v1/supplier/invoice/invoices" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  --data-urlencode "statuses=approved,processing,paid" \
  --data-urlencode "buyerCompanyId=42" \
  --data-urlencode "markedPaidAtStartDate=08/01/2026 00:00:00" \
  --data-urlencode "markedPaidAtEndDate=08/31/2026 00:00:00" \
  -d limit=25 -d sort_by=createdAt -d order=desc

# Pending proposals on one work order
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/supplier/quote/proposals?status=pending&workOrderId=9001"
```

**Both lists**

| Filter | Matches |
| --- | --- |
| `status`, `statuses` | The status, lowercase. Proposals: `draft`, `pending`, `awarded`, `declined`. Invoices: `draft`, `pending`, `approved`, `processing`, `paid`, `disputed`, `pastdue`, `transferred`, `void`. |
| `workOrderId` | Records for one work order. |
| `buyerCompanyId` | Records for one of your buyer customers. It narrows your results; it can't widen them. |
| `locationId`, `locationIds` | Records for these locations. |
| `regionIds` | Records for locations in these regions. |
| `problemTypeIds` | Records whose work order has these problem types. |
| `woPriorityIds` | Records whose work order has these priorities. |
| `isCapex` | `true` returns only records for work orders flagged as capital expenditure; `false` leaves them out. |
| `createdAtStartDate`, `createdAtEndDate` | Records created within the window. |
| `approvedAtStartDate`, `approvedAtEndDate` | Proposals awarded, or invoices approved, within the window. |
| `workCompletedAtStartDate`, `workCompletedAtEndDate` | Records whose work order was completed within the window. |

**Proposals only**

| Filter | Matches |
| --- | --- |
| `search` | Part of the work order title. A numeric value also matches the proposal id or the work order id exactly. |

**Invoices only**

| Filter | Matches |
| --- | --- |
| `search` | Part of the work order title, or exactly one of: work order id, external work order id, invoice number, invoice id, PO number, GL code. |
| `invoiceNumber` | Invoices with this invoice number. |
| `externalWorkOrderId` | Invoices for one work order, by the buyer's external reference on it. |
| `workOrderDisplayStatus` | Invoices whose work order is in this display status: `Pending`, `Deferred`, `Open`, `InProgress`, `OnHold`, `Completed`, or `Cancelled`. |
| `assetId`, `assetIds` | Invoices whose work order is on these assets. |
| `problemTypeId` | Invoices whose work order has this problem type. |
| `isPM` | `true` returns only invoices for preventive maintenance work orders; `false` leaves them out. |
| `publishedAtStartDate`, `publishedAtEndDate` | Invoices published to the buyer within the window. |
| `processedAtStartDate`, `processedAtEndDate` | Invoices the buyer moved to `processing` within the window. |
| `markedPaidAtStartDate`, `markedPaidAtEndDate` | Invoices marked paid within the window. Useful for AR reconciliation. |
| `dueAtStartDate`, `dueAtEndDate` | Invoices due within the window. |

Value rules:

- **Sorting.** Both lists sort by `createdAt`, `id`, `workOrderId`, `locationId`, `supplierFacilityId`, or `buyerFacilityId`; invoices also sort by `invoiceTotalAfterTax`, and proposals by `updatedAt` and `totalAfterTax`. Once you set `sort_by`, `order` defaults to `asc`, so send `order=desc` for newest first. With no `sort_by`, invoices come newest first and proposals come in `id` order (oldest first). An unsupported `sort_by` on proposals also falls back to `id` order.
- **Lists take commas with no spaces.** A singular key (`status`) takes one value; the plural key takes a comma-separated list. `status=pending,approved` looks for one status with that literal name and returns nothing. A space after a comma can fail the request.
- **One value per key.** If you repeat a parameter, only the first is used.
- **Dates use `MM/dd/yyyy HH:mm:ss` in UTC**, for example `08/01/2026 00:00:00`. The time is required. The start bound is inclusive at the time you send; the end bound covers the whole end day (its time is replaced with 23:59:59). URL-encode the value. A date that does not parse is read as 1 January 1970 rather than rejected, so a bad start date matches everything and a bad end date matches nothing.
- **Values must be well formed.** A non-numeric id, or a boolean other than `true` or `false`, can fail the request with a `500` rather than a `400`.
- **Unrecognized filters are ignored**, and your tenant scoping can't be overridden: `supplierFacilityId` is always set from your API key.

## End-to-end billing flow

1. Work order reaches quoting: submit a proposal, wait for `awarded`.
2. Complete the work through [service-call check-out](/supplier-api/service-calls#3-check-out-and-set-the-outcome).
3. Create the draft invoice; generate your PDF.
4. Once the work order shows Completed, `upload_and_publish`.
5. Poll invoice status until `paid`, and reconcile against `markedPaidAt`.
