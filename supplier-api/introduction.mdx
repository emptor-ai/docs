The OpenWrench Supplier API gives service providers programmatic access to their side of the platform. Use it to receive and update work orders, schedule and document service calls, submit quotes and invoices, pull WrenchMode technician time data, and manage purchasing and inventory.

## Base URL

```text
https://api.useopenwrench.com/api/external
```

All supplier endpoints are under `/v1/supplier/`.

## Authentication

Every request must carry **two headers**: `X-API-KEY` (your API key, issued per supplier contact) and `OW-KEY` (the OpenWrench shared secret issued alongside it). The key automatically scopes every request to your facility. You only ever see work orders, invoices, and data that belong to you. Requests missing either header return `401`.

```bash
curl -H "X-API-KEY: <your-key>" -H "OW-KEY: <shared-secret>" \
  "https://api.useopenwrench.com/api/external/v1/supplier/ping"
```

To get an API key and shared secret, contact [support@useopenwrench.com](mailto:support@useopenwrench.com).

Keys do not expire on their own. To rotate one, request a new key/shared-secret pair from support, deploy the new pair, then ask support to revoke the old one.

## Rate limits

10 requests per 20-second window per key. Beyond that you'll receive `429 Too Many Requests`. Wait at least 20 seconds before retrying, and space background jobs (such as full paginated exports) so they stay under the cap.

## Keeping work orders in sync

Most supplier integrations exist to mirror the OpenWrench work order queue into another system. Build that on push, not polling:

1. Register a [webhook](/supplier-api/webhooks) endpoint. OpenWrench sends `workorder.create`, `workorder.status_update`, and `workorder.new_note` events as they happen.
2. On each event, fetch that one work order with `GET /v1/supplier/work_order/work_orders/{id}`.
3. Use `GET /v1/supplier/work_order/work_orders` only for the one-time initial load and for occasional reconciliation, with a narrow filter and a small page.

Do not poll the list endpoint on a schedule to find new or changed work. It is the most expensive read in the API, it is slow on large queues, and it competes with your real work for the rate limit. See [Work orders](/supplier-api/work-orders#reading-your-queue) for the details.

## Response envelope

Single-entity responses:

```json
{ "type": "WorkOrder", "data": { "...": "..." }, "status": "ok" }
```

List responses add a total `count`:

```json
{ "type": "WorkOrder", "data": [ "..." ], "count": 42, "status": "ok" }
```

Errors:

```json
{ "message": "Human-readable message", "type": "NotFoundException", "status": "error", "traceId": "abc123def45" }
```

`401` means a missing or invalid key; `400` covers bad input, bad filters, and permission denials; `429` is the rate limit.

## Pagination and filtering

List endpoints accept `offset`, `limit` (default 10, max 25), `sort_by`, and `order` (`asc` | `desc`). The API treats additional query parameters as filters. Each endpoint supports its own set of filter keys, and keys it does not recognize are ignored rather than rejected. Multi-value filters use a plural key with comma-separated values (`statuses=TechScheduled,TechRescheduled`). For work orders, see the [filter reference](/supplier-api/work-orders#filter-reference).

## Date formats

Most timestamps are ISO 8601 strings with offset (for example, `2026-08-14T13:05:22.000-07:00`); some database timestamp fields serialize as `yyyy-MM-dd HH:mm:ss.S`. Plain dates are `yyyy-MM-dd`.

When sending date-times, use ISO 8601 with a `T` between the date and time and an explicit offset. A space-separated value such as `2026-09-10 10:43:00+00:00` is not ISO 8601, and the API rejects it. Send `2026-09-10T10:43:00.000+00:00` instead. UTC may be written as `+00:00` or `Z`.

Date filters on the invoice, proposal, and work order lists are the exception. They take `MM/dd/yyyy HH:mm:ss`, a local wall-clock time with no offset, for example `10/09/2026 00:00:00`:

- **Time zone.** Pass the optional `timezone` query parameter to set the zone OpenWrench reads the values in. Use an IANA zone name, such as `America/Chicago`, `America/New_York`, or `UTC`. Names are case-sensitive. Without `timezone`, OpenWrench reads values in UTC.
- **Rejected zones.** Fixed offsets (`-05:00`, `GMT-5`, `Z`, `Etc/GMT+5`), abbreviations (`CST`), and unknown names return `400`.
- **No offset in the value.** OpenWrench ignores an offset such as `-05:00` at the end of a filter value. Use `timezone` instead.
- **Malformed values return `400`.** A value that doesn't match the format returns `400`, for example `Invalid markedPaidAtStartDate. Expected format MM/dd/yyyy HH:mm:ss`. That includes ISO 8601 values (`2026-10-09T00:00:00`), dates without a time (`10/09/2026`), and values of only spaces. OpenWrench still reads an empty value as 1 January 1970.
- **End bounds.** Invoice and proposal end dates cover the whole end day: OpenWrench replaces the time with 23:59:59 on that date in `timezone`. Work order end dates are exact, so send `23:59:59` to include the whole day.
- **Daylight saving time.** A time in the skipped hour of a spring-forward change moves forward by the length of the gap. A time in the repeated hour of a fall-back change means the standard-time occurrence, which is the second one.

For example, this request returns invoices marked paid on October 9, 2026, Central time:

```bash
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/supplier/invoice/invoices?markedPaidAtStartDate=10/09/2026%2000:00:00&markedPaidAtEndDate=10/09/2026%2000:00:00&timezone=America/Chicago"
```

For each list's filters, see the filter value rules for [work orders](/supplier-api/work-orders#filter-value-rules) and for [proposals and invoices](/supplier-api/quotes-and-invoicing#filtering-lists).

## Technician time data

The WrenchMode endpoints expose per-technician work and drive time: `GET /v1/supplier/wrench_mode/events/analytics/{fromDate}/{toDate}` returns a per-technician drive/work/total rollup (window capped at 1 month). `GET /v1/supplier/wrench_mode/events` returns the raw event log behind it. Service-call expansions (`/with_work_logs`, `/with_tech_details`) give the per-visit story.
