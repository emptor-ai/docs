The OpenWrench Buyer API gives facility operators programmatic access to everything on the buyer side of the platform. You can use it for creating and tracking work orders, managing assets and locations, reviewing quotes and invoices, monitoring preventive maintenance, and querying your supplier network.

## Base URL

```text
https://api.useopenwrench.com/api/external
```

All buyer endpoints are under `/v1/buyer/`.

## Authentication

Every request must carry **two headers**: `X-API-KEY` (your API key, issued per buyer contact) and `OW-KEY` (the OpenWrench shared secret issued alongside it). The key automatically scopes every request to your company, so you only ever see your own data. Requests missing either header return `401`.

```bash
curl -H "X-API-KEY: <your-key>" -H "OW-KEY: <shared-secret>" \
  "https://api.useopenwrench.com/api/external/v1/buyer/ping"
```

To get an API key and shared secret, contact [support@useopenwrench.com](mailto:support@useopenwrench.com). Use `GET /v1/buyer/me` to inspect the identity (contact, facility, company) behind your key.

Keys do not expire on their own. To rotate one, request a new key/shared-secret pair from support, deploy the new pair, then ask support to revoke the old one.

<Note>
The **Internal Teams API** section further down this tab uses a **separate partner API key**. Your buyer key will not authenticate against those `/v1/partners/` endpoints. See the [Internal Teams API introduction](/partners-api/introduction) for details.
</Note>

## Rate limits

10 requests per 20-second window per key. Beyond that you'll receive `429 Too Many Requests`. Wait at least 20 seconds before retrying, and space background jobs (such as full paginated exports) so they stay under the cap.

## Keeping work orders in sync

If your integration mirrors work orders into another system (a ticketing tool, an ERP, a data warehouse), build it on push, not polling:

1. Register a [webhook](/buyer-api/webhooks) endpoint. OpenWrench sends `workorder.create`, `workorder.status_update`, and `workorder.new_note` events as they happen.
2. On each event, fetch that one work order with `GET /v1/buyer/work_order/work_orders/{id}`.
3. Use `GET /v1/buyer/work_order/work_orders` for ad-hoc queries, the one-time initial load, and occasional reconciliation, with a narrow filter and a small page.

Do not poll the list endpoint on a schedule to find new or changed work orders. It is the most expensive read in the API, it is slow on large accounts, and it competes with your real work for the rate limit. See [Work orders](/buyer-api/work-orders#list-filter-and-count) for the details.

## Response envelope

Single-entity responses:

```json
{ "type": "WorkOrder", "data": { "...": "..." }, "status": "ok" }
```

List responses add a total `count`:

```json
{ "type": "WorkOrder", "data": [ "..." ], "count": 42, "status": "ok" }
```

Errors:

```json
{ "message": "Human-readable message", "type": "NotFoundException", "status": "error", "traceId": "abc123def45" }
```

`401` means a missing or invalid key; `400` covers bad input, bad filters, and permission denials; `429` is the rate limit.

## Pagination and filtering

List endpoints accept `offset`, `limit`, `sort_by`, and `order` (`asc` or `desc`; anything other than `asc` sorts descending, and `asc` is the default). `limit` defaults to 10 and goes up to 25. A `limit` above 25 isn't clamped: it's ignored and you get the default page of 10. The location list is capped at 10 per page.

The API reads every other query parameter as a filter. Filters combine with AND, and always with the tenant scoping derived from your key, so you only ever see your company's records. Each endpoint supports its own set of filter keys:

| Endpoint | Filter reference |
| --- | --- |
| Work orders | [Work order filters](/buyer-api/work-orders#filter-reference) |
| Invoices | [Invoice filters](/buyer-api/invoices#filter-reference) |
| Quotes and proposals | [Proposal filters](/buyer-api/quotes-and-proposals#filter-reference) |
| Locations and assets | [Location filters](/buyer-api/assets-and-locations#location-filters) and [asset filters](/buyer-api/assets-and-locations#asset-filters) |
| Planned maintenance | [Schedule filters](/buyer-api/planned-maintenance#filter-reference) |
| Site survey walkthroughs | [Walkthrough filters](/buyer-api/site-survey-walkthroughs#filter-reference) |

### Filter value rules

These rules apply to every list except work orders, which resolve filters in a search index and have [their own rules](/buyer-api/work-orders#filter-value-rules).

- **Keys are case-sensitive.** A query parameter that isn't a supported filter, including a misspelled key, is ignored rather than rejected, and the request still succeeds. Before relying on a new filter, compare a count with and without it.
- **Use the plural key for several values.** A singular key (`status`) takes one value; the plural key (`statuses`) takes a comma-separated list and matches any of the values. Don't put spaces after the commas. If you repeat a parameter, only the first value is used.
- **Ids are whole numbers.** A malformed id never widens the result: it matches nothing, or fails the request with a `500` rather than a `400`.
- **Booleans are `true` or `false`.**
- **Dates use `MM/dd/yyyy HH:mm:ss` in UTC**, for example `08/01/2026 00:00:00`. URL-encode the value (`curl -G --data-urlencode` does this for you). A `…StartDate` filter starts at the time you give. A `…EndDate` filter covers the whole day you name, whatever time you send. A date that doesn't parse is read as 1 January 1970, so a bad start date matches everything and a bad end date matches nothing. Planned maintenance `nextScheduledStartAt` and `nextScheduledEndAt` are the exception: they take `yyyy-MM-ddTHH:mm:ss`.
- **Tenant scoping can't be overridden.** `buyerCompanyId` is always set from your API key, so passing it has no effect.

## Date formats

Most timestamps are ISO 8601 strings with offset (for example, `2026-08-14T13:05:22.000-07:00`); some database timestamp fields serialize as `yyyy-MM-dd HH:mm:ss.S`. Plain dates are `yyyy-MM-dd`. When sending date-times, use ISO 8601. Date filters on list endpoints are the exception: they take `MM/dd/yyyy HH:mm:ss` in UTC (see [filter value rules](#filter-value-rules)).
