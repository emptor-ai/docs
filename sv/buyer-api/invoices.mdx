Leverantörer fakturerar avslutade arbetsordrar via fakturor; Buyer API är där din AP-integration läser dem, för dem genom godkännande och markerar dem betalda. Fakturor kan även förankras till ett projekt i stället för en arbetsorder. Samma statusar och betalslutpunkter gäller, med skillnaderna beskrivna nedan.

Alla exempel förutsätter:

```bash
export BASE="https://api.useopenwrench.com/api/external"
export KEY="<your-api-key>"
export SECRET="<shared-secret>"
```

## Fakturastatusar

Fakturor bär en gemen `status`:

| Status | Betydelse |
| --- | --- |
| `draft` | Leverantören redigerar fortfarande. **Aldrig synlig i köparläsningar.** |
| `pending` | Publicerad till dig, väntar på granskning. |
| `approved` | Godkänd för betalning. |
| `processing` | I din betalningskörning. |
| `paid` | Avräknad. |
| `disputed` | Du har bestridit den (upprättad i appen). |
| `pastdue`, `transferred`, `void` | Åldrande, överlämnad och ogiltigförklarad. |

Den köparkontrollerade vägen är `pending → approved → processing → paid`. Varje flytt har en dedikerad slutpunkt; det finns ingen generisk statussättare.

## Läsa fakturor

```bash
# Väntande fakturor, nyast först
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/buyer/invoice/invoices?status=pending&sort_by=createdAt&order=desc&limit=25"

# Endast antal
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/buyer/invoice/invoices/count_by?status=pending"

# En faktura
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" "$BASE/v1/buyer/invoice/invoices/7710"
```

En faktura länkar tillbaka till sitt `supplierFacilityId` plus **exakt ett** av `workOrderId` eller `projectId` (det andra är `null`, tillsammans med den hydrerade `workOrder` / `project`). Arbetsorderfakturor bär alltid `locationId` och `buyerFacilityId`; projektfakturor bär dem endast när klienten angav dem, så båda kan vara `null`. Fakturan bär pengauppdelningen i sektioner (arbete, material, resa, frakt, övrigt), var och en med rader, en `taxRate` och en `totalBeforeTax`, som rullar upp till `invoiceTotalBeforeTax`, `invoiceTax` och `invoiceTotalAfterTax`. Monetära värden serialiseras som strängar. En kort AI-härledd sammanfattning av omfattningen kan visas i `title`. Den renderade PDF:en finns i `invoicePDFs`; stödjande filer finns i `attachments` (se [Filer och bilagor](/sv/buyer-api/files-and-attachments)).

### Lista, filtrera och räkna

```bash
# Godkända fakturor på två platser, publicerade i augusti, största först
curl -G "$BASE/v1/buyer/invoice/invoices" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  --data-urlencode "status=approved" \
  --data-urlencode "locationIds=1204,1310" \
  --data-urlencode "publishedAtStartDate=08/01/2026 00:00:00" \
  --data-urlencode "publishedAtEndDate=08/31/2026 00:00:00" \
  -d limit=25 -d sort_by=invoiceTotalAfterTax -d order=desc

# Endast projektfakturor för det här projektet
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/buyer/invoice/invoices?invoiceEntityType=project&projectId=482"
```

`GET /invoices`, `/invoices/count_by` och `/invoices/download` tar samma filter från [filterreferensen](#filterreferens) nedan. Filter kombineras med AND och kombineras alltid med tenant-avgränsningen som härleds från din nyckel. Leverantörsutkast och ogiltigförklarade fakturor returneras aldrig, oavsett vad du filtrerar på.

- **Sortering.** `sort_by` stöder `createdAt`, `invoiceTotalAfterTax`, `id`, `workOrderId`, `locationId`, `supplierFacilityId` och `buyerFacilityId`. Utan `sort_by` kommer resultaten nyast först. När du sätter `sort_by` blir `order` som standard `asc`, så skicka `order=desc` för fallande ordning. Andra fält, till exempel `publishedAt`, går inte att sortera på; filtrera på ett `publishedAt`-fönster istället.
- **Okända filter ignoreras.** Varje frågeparameter som inte finns i filterreferensen ignoreras istället för att avvisas, och anropet lyckas ändå. Innan du förlitar dig på ett nytt filter, jämför `count_by` med och utan det.

### Filterreferens

Nycklarna är skiftlägeskänsliga. En nyckel i singular (`status`) tar ett värde; nyckeln i plural (`statuses`) tar en kommaseparerad lista och matchar något av värdena.

**Status**

| Filter | Matchar |
| --- | --- |
| `status`, `statuses` | Fakturans status, med gemener: `pending`, `approved`, `processing`, `paid`, `disputed`, `pastdue` eller `transferred`. Se [fakturastatusar](#fakturastatusar). |
| `invoiceEntityType` | `work_order` returnerar endast arbetsorderfakturor; `project` returnerar endast [projektfakturor](#projektfakturor). Utelämna det för att få båda. |
| `workOrderDisplayStatus` | Fakturor vars arbetsorder har denna visningsstatus: `Pending`, `Deferred`, `Open`, `InProgress`, `OnHold`, `Completed` eller `Cancelled`. |

**Vad och var**

| Filter | Matchar |
| --- | --- |
| `search` | En del av arbetsorderns titel, eller exakt ett av: arbetsorder-id, externt arbetsorder-id, fakturanummer, faktura-id, PO-nummer, GL-kod. |
| `workOrderId` | Fakturor för en arbetsorder. |
| `externalWorkOrderId` | Fakturor för en arbetsorder, via den externa referens som ditt system lagrar på den. |
| `projectId` | Fakturor förankrade till ett projekt. |
| `buyerProjectId` | Fakturor för arbetsordrarna i ett projekt. En arbetsorder listar sina projekt i `buyerProjectIds`. |
| `invoiceNumber` | Fakturor med detta leverantörsfakturanummer. |
| `locationId`, `locationIds` | Fakturor för dessa platser. Hämta plats-id:n från [`GET /v1/buyer/location/locations`](/sv/buyer-api/assets-and-locations#platser). |
| `regionIds` | Fakturor för platser i dessa regioner. |
| `assetId`, `assetIds` | Fakturor vars arbetsorder gäller dessa tillgångar. |
| `problemTypeId`, `problemTypeIds` | Fakturor vars arbetsorder har dessa problemtyper. Hämta id:n från [`GET /v1/buyer/work_order/problem_types`](/sv/buyer-api/work-orders#problemtyper). |
| `woPriorityIds` | Fakturor vars arbetsorder har dessa prioriteter. |
| `isPM` | `true` returnerar endast fakturor för arbetsordrar för förebyggande underhåll; `false` utesluter dem. |
| `isCapex` | `true` returnerar endast fakturor för arbetsordrar flaggade som investeringsutgift (capex); `false` utesluter dem. |

**Vem och bokföring**

| Filter | Matchar |
| --- | --- |
| `supplierFacilityId`, `supplierFacilityIds` | Fakturor från dessa leverantörer. Hämta leverantörsanläggnings-id:n från [`GET /v1/buyer/supplier_facilities`](/sv/buyer-api/supplier-network#ditt-leverantörsnätverk). |
| `hasPONumber` | `true` returnerar fakturor som har ett PO-nummer; `false` returnerar fakturor utan. |
| `hasGLCode` | `true` returnerar fakturor som har en GL-kod; `false` returnerar fakturor utan. |

**Datum**

| Filter | Matchar |
| --- | --- |
| `createdAtStartDate`, `createdAtEndDate` | Fakturor skapade inom fönstret. |
| `publishedAtStartDate`, `publishedAtEndDate` | Fakturor som leverantören publicerade till dig inom fönstret. |
| `approvedAtStartDate`, `approvedAtEndDate` | Fakturor godkända inom fönstret. |
| `processedAtStartDate`, `processedAtEndDate` | Fakturor flyttade till `processing` inom fönstret. |
| `markedPaidAtStartDate`, `markedPaidAtEndDate` | Fakturor markerade som betalda inom fönstret. |
| `dueAtStartDate`, `dueAtEndDate` | Fakturor som förfaller inom fönstret. |
| `workCompletedAtStartDate`, `workCompletedAtEndDate` | Fakturor vars arbetsorder slutfördes inom fönstret. |

### Regler för filtervärden

- **Använd pluralnyckeln för flera värden, utan mellanslag.** `statuses=approved,processing` matchar någon av statusarna. `status=approved,processing` letar efter en enda status med just det namnet och returnerar ingenting. Ett mellanslag efter ett kommatecken i en id-lista kan få anropet att misslyckas.
- **Ett värde per nyckel.** Om du upprepar en parameter används bara den första.
- **Datum använder `MM/dd/yyyy HH:mm:ss` i UTC**, till exempel `08/01/2026 00:00:00`. Tiden är obligatorisk. Startgränsen är inkluderande från den tid du skickar. Slutgränsen täcker hela slutdagen: dess tid ersätts med 23:59:59. URL-koda värdet (`curl -G --data-urlencode` gör det åt dig). Ett datum som inte kan tolkas avvisas inte. Det läses som 1 januari 1970, så ett felaktigt startdatum matchar allt och ett felaktigt slutdatum matchar ingenting.
- **Booleska värden är `true` eller `false`.** Alla andra värden, eller ett icke-numeriskt id, kan få anropet att misslyckas med `500` istället för `400`.
- **Tenant-avgränsningen kan inte åsidosättas.** `buyerCompanyId` sätts alltid från din API-nyckel, så att skicka det har ingen effekt.

### Plattad export

`GET /v1/buyer/invoice/invoices/download` returnerar samma data som platta rader (en rad per faktura med totalsummorna denormaliserade), byggd för kalkylbladsexport och AP-systemimporter. Samma filter som list-slutpunkten. På projektfaktura-rader är `workOrderId`, `workOrderTitle`, `problemTypeId`, `problemTypeName`, `locationId` och `locationName` `null`; `projectId` är satt.

## Flytta en faktura genom godkännande

Varje övergångsslutpunkt tar bara fakturans id:

```bash
curl -X POST "$BASE/v1/buyer/invoice/status/approved" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "id": 7710 }'
```

De fyra slutpunkterna är `status/pending`, `status/approved`, `status/processing` och `status/paid`. Delat beteende:

- Varje övergång **rensar fakturans tvistflagga** och sprider sedan en matchande statusändring till den associerade arbetsordern.
- Om statusmappningen för arbetsordern misslyckas **ogiltigförklaras** fakturan och anropet returnerar `400`. Behandla `400` här som "hämta om och inspektera", inte "försök igen".
- Ett spar-nivåvalideringsfel returnerar `406`.

### Markera betald efter arbetsorder-id

När ditt AP-system känner till arbetsordern men inte OpenWrench-fakturans id, stäng loopen med:

```bash
curl -X POST "$BASE/v1/buyer/invoice/status/paid/by_work_order_id" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "workOrderId": "9001" }'
```

Uppslagningen provar `workOrderId` först och faller tillbaka på `externalWorkOrderId`, alltid inom ditt företag. Redan `paid` fakturor returneras oförändrade (säkert att försöka igen); `approved` eller `processing` fakturor markeras som betalda; en faktura i någon annan status returnerar `400` med "Invoice not found".

## Projektfakturor

Projektfakturor är förankrade till ett projekt (`projectId`) i stället för en arbetsorder (`workOrderId`), och hoppar över arbetsordersidan av pipelinen. För en faktura utan `workOrderId` hoppar OpenWrench över:

- NTE-kontrollen vid skapande och uppdatering.
- Härledning av GL-kod från arbetsordern.
- Speglingen av budgetutgifter och tillgångsutgifter.
- Statussynken mot arbetsordern som normalt körs vid varje statusövergång (en statusövergång på en projektfaktura ogiltigförklarar aldrig och returnerar `400` för en trasig WO-mappning).
- Tillägget av arbetsorderns detaljsida i faktura-PDF-verktyget.
- WO-förankrade godkännandehierarkier och deras godkännande-, påminnelse- och eskaleringsnotifieringar.
- Per-WO-dubblettkontrollen "en faktura per leverantör".
- Den valutabegränsade valideringen av `taxLineItems` (belopp valideras fortfarande som numeriska).

Analyser för kostnad-per-plats och kostnad-per-anläggning inkluderar endast fakturor som bär respektive fält. En projektfaktura skapad utan `locationId` eller `buyerFacilityId` visas inte i dessa rapporter.

Genvägen `POST status/paid/by_work_order_id` matchar endast arbetsorderfakturor; för en projektfaktura, markera som betald via `id` med `POST status/paid`.

## Verktyg

**Lägg till arbetsorderdetaljsidan till PDF:en.** `PATCH /v1/buyer/invoice/file/invoice_pdf/add_work_order_detail_page/{invoiceId}` genererar om fakturans PDF med arbetsorderdetaljsidan bifogad och returnerar den nya PDF-länken (höljestyp `UpdatedInvoicePdf`). Ingen förfrågan-kropp; inte hastighetsbegränsad.

**Massuppdatering med filter.** `PATCH /v1/buyer/invoice/bulk_update_with_filters` tillämpar en kolumnuppdatering på varje faktura som matchar ett filter, alltid begränsat till ditt företag. Båda kartorna är fria kolumn→värde-mappningar:

```bash
curl -X PATCH "$BASE/v1/buyer/invoice/bulk_update_with_filters" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "filters": { "status": "approved" }, "updates": { "status": "processing" } }'
```

Den returnerar antalet uppdaterade fakturor. Det här är ett kraftverktyg som förbigår sidoeffekterna från per-faktura-övergångar, så föredra statusslutpunkterna om du inte verkligen behöver en sweep. Inte hastighetsbegränsad.

**Publicera utkast för avslutade arbetsordrar.** `PATCH /v1/buyer/invoice/publish_draft_invoices_if_wo_complete_and_auto_publish_enabled` publicerar leverantörsfakturautkast vars arbetsorder är klar, för leverantörer som aktiverade auto-publicering. Det kräver en **super-admin** köpar-API-nyckel och returnerar `403` för en vanlig nyckel. Avsett för schemalagda skötseljobb.

## AP-synk-mönster

En robust leverantörsreskontrasynk:

1. Polla `GET /invoices?status=pending` (eller `publishedAt`-fönster) enligt schema.
2. Hämta varje faktura. För arbetsorderfakturor, matcha totalsummor mot det godkända [förslaget](/sv/buyer-api/quotes-and-proposals) och arbetsorderns `nte`. För projektfakturor, matcha mot din projektbudget i stället. NTE-kontrollen körs inte på serversidan för projektfakturor.
3. `POST status/approved`, exportera till ditt AP-system och sedan `POST status/processing`.
4. Vid avräkning, `POST status/paid` via id, eller `status/paid/by_work_order_id` med den arbetsorderreferens som ditt AP-system bär.
5. Logga höljets `traceId` vid varje `400`/`406` så att supporten kan spåra den exakta förfrågan.
