OpenWrench Supplier API ger serviceleverantörer programmatisk åtkomst till sin sida av plattformen: ta emot och uppdatera arbetsordrar, schemalägga och dokumentera servicebesök, skicka in offerter och fakturor, hämta WrenchMode-tekniktid och hantera inköp och lager.

## Bas-URL

```text
https://api.useopenwrench.com/api/external
```

Alla leverantörsslutpunkter ligger under `/v1/supplier/`.

## Autentisering

Varje förfrågan måste innehålla **två rubriker**: `X-API-KEY` (din API-nyckel, utfärdad per leverantörskontakt) och `OW-KEY` (den delade hemligheten från OpenWrench som utfärdas tillsammans med den). Nyckeln avgränsar automatiskt varje förfrågan till din anläggning. Du ser bara arbetsordrar, fakturor och data som tillhör dig. Förfrågningar som saknar någon av rubrikerna returnerar `401`.

```bash
curl -H "X-API-KEY: <your-key>" -H "OW-KEY: <shared-secret>" \
  "https://api.useopenwrench.com/api/external/v1/supplier/ping"
```

För att få en API-nyckel och en delad hemlighet, kontakta [support@useopenwrench.com](mailto:support@useopenwrench.com).

Nycklar löper inte ut av sig själva. För att rotera en, begär ett nytt par nyckel/delad hemlighet från supporten, driftsätt det nya paret och be sedan supporten återkalla det gamla.

## Hastighetsgränser

10 förfrågningar per 20-sekundersfönster per nyckel. Utöver det får du `429 Too Many Requests`: vänta minst 20 sekunder innan du försöker igen, och sprid ut bakgrundsjobb (till exempel fullständiga sidindelade exporter) så att de håller sig under gränsen.

## Hålla arbetsordrar synkroniserade

De flesta leverantörsintegrationer finns till för att spegla OpenWrench-arbetsorderkön till ett annat system. Bygg det på push, inte polling:

1. Registrera en [webhook](/sv/supplier-api/webhooks)-slutpunkt. OpenWrench skickar händelserna `workorder.create`, `workorder.status_update` och `workorder.new_note` när de inträffar.
2. Vid varje händelse, hämta just den arbetsordern med `GET /v1/supplier/work_order/work_orders/{id}`.
3. Använd `GET /v1/supplier/work_order/work_orders` endast för den engångsvisa initiala laddningen och för tillfällig avstämning, med ett smalt filter och en liten sida.

Polla inte list-slutpunkten enligt schema för att hitta nytt eller ändrat arbete. Den är den dyraste läsningen i API:et, den är långsam på stora köer och den konkurrerar med ditt riktiga arbete om hastighetsgränsen. Se [Arbetsordrar](/sv/supplier-api/work-orders#läsa-din-kö) för detaljerna.

## Svarshöljet

Svar för enskilda entiteter:

```json
{ "type": "WorkOrder", "data": { "...": "..." }, "status": "ok" }
```

Listsvar lägger till ett totalt `count`:

```json
{ "type": "WorkOrder", "data": [ "..." ], "count": 42, "status": "ok" }
```

Fel:

```json
{ "message": "Human-readable message", "type": "NotFoundException", "status": "error", "traceId": "abc123def45" }
```

`401` betyder att uppgifter saknas eller är ogiltiga; `400` täcker felaktig indata, felaktiga filter och behörighetsavslag; `429` är hastighetsgränsen.

## Paginering och filtrering

List-slutpunkter accepterar `offset`, `limit` (standard 10, max 25), `sort_by` och `order` (`asc` | `desc`). Ytterligare frågeparametrar behandlas som filter. Varje slutpunkt stöder sin egen uppsättning filternycklar, och nycklar den inte känner igen ignoreras i stället för att avvisas. Filter med flera värden använder en pluralnyckel med kommaseparerade värden (`statuses=TechScheduled,TechRescheduled`). För arbetsordrar, se [filterreferensen](/sv/supplier-api/work-orders#filterreferens).

## Datumformat

De flesta tidsstämplar är ISO 8601-strängar med offset (till exempel `2026-08-14T13:05:22.000-07:00`); vissa databastidsstämpelfält serialiseras som `yyyy-MM-dd HH:mm:ss.S`. Rena datum är `yyyy-MM-dd`.

När du skickar datum-tider, använd ISO 8601 med ett `T` mellan datum och tid och en explicit offset. Ett mellanslagsseparerat värde som `2026-09-10 10:43:00+00:00` är inte ISO 8601 och avvisas; skicka `2026-09-10T10:43:00.000+00:00` i stället. UTC kan skrivas som `+00:00` eller `Z`.

Datumfilter i faktura-, förslags- och arbetsorderlistorna är undantaget. De tar `MM/dd/yyyy HH:mm:ss`, en lokal klocktid utan offset, till exempel `10/09/2026 00:00:00`:

- **Tidszon.** Skicka den valfria frågeparametern `timezone` för att ange vilken zon värdena läses i. Använd ett IANA-zonnamn, som `America/Chicago`, `America/New_York` eller `UTC`. Namnen är skiftlägeskänsliga. Utan `timezone` läses värdena i UTC.
- **Avvisade zoner.** Fasta offset (`-05:00`, `GMT-5`, `Z`, `Etc/GMT+5`), förkortningar (`CST`) och okända namn returnerar `400`.
- **Ingen offset i värdet.** OpenWrench ignorerar en offset som `-05:00` i slutet av ett filtervärde. Använd `timezone` i stället.
- **Felformaterade värden returnerar `400`.** Ett värde som inte matchar formatet returnerar `400`, till exempel `Invalid markedPaidAtStartDate. Expected format MM/dd/yyyy HH:mm:ss`. Det gäller även ISO 8601-värden (`2026-10-09T00:00:00`), datum utan tid (`10/09/2026`) och värden som bara består av mellanslag. Ett tomt värde läses fortfarande som 1 januari 1970.
- **Slutgränser.** Slutdatum för fakturor och förslag täcker hela slutdagen: OpenWrench ersätter tiden med 23:59:59 på det datumet i `timezone`. Slutdatum för arbetsordrar är exakta, så skicka `23:59:59` för att ta med hela dagen.
- **Sommartid.** En tid i den överhoppade timmen vid övergång till sommartid flyttas framåt med glappets längd. En tid i den upprepade timmen vid övergång till normaltid avser förekomsten i normaltid, alltså den andra.

Den här förfrågan returnerar till exempel fakturor som markerades som betalda den 9 oktober 2026, Central time:

```bash
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/supplier/invoice/invoices?markedPaidAtStartDate=10/09/2026%2000:00:00&markedPaidAtEndDate=10/09/2026%2000:00:00&timezone=America/Chicago"
```

Filtren för respektive lista finns i reglerna för filtervärden för [arbetsordrar](/sv/supplier-api/work-orders#regler-för-filtervärden) och för [förslag och fakturor](/sv/supplier-api/quotes-and-invoicing#filtrera-listor).

## Teknikertid

WrenchMode-slutpunkterna exponerar per-tekniker arbets- och körtid: `GET /v1/supplier/wrench_mode/events/analytics/{fromDate}/{toDate}` returnerar en per-tekniker sammanställning av körning/arbete/totalt (fönster max 1 månad), och `GET /v1/supplier/wrench_mode/events` returnerar den råa händelseloggen bakom det. Servicebesöks-utökningarna (`/with_work_logs`, `/with_tech_details`) ger den per-besök-historien.
