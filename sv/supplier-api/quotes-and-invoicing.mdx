Pengar flödar genom två objekt: **förslag** (offerter som köparen godkänner innan arbetet fortsätter) och **fakturor** (räkningen för utfört arbete). Leverantörer skapar båda genom det här API:et.

<Note>
Ingen av slutpunkterna är tillgänglig för interna serviceteams nycklar; offerering och fakturering är för tredjepartsleverantörer som fakturerar en köpare.
</Note>

Alla exempel förutsätter:

```bash
export BASE="https://api.useopenwrench.com/api/external"
export KEY="<your-api-key>"
export SECRET="<shared-secret>"
```

## Pengar är strängar, i sektioner

Förslag och fakturor delar en radstruktur. Belopp är **strängar som måste parsas som tal** ("450.00", inte 450.00 som ett flyttal; avsändare bör formatera med två decimaler och parsa som decimaler). Sektionerna är arbete, material, resa, frakt och övrigt (förslag lägger till inkommen kostnad), var och en med sina egna rader, en skattesats och `...TotalBeforeTax`, som rullar upp till före-skatt, skatt och efter-skatt-totaler. Rader för resa, frakt och övrigt är enkla `{ "description", "amount" }`-objekt.

## Förslag (offerter)

`POST /v1/supplier/quote/proposals` skapar förslaget direkt i **`pending`**-status under din anläggning; det finns inget separat inlämningssteg. Krävs: `workOrderId` och `totalAfterTax`.

```bash
curl -X POST "$BASE/v1/supplier/quote/proposals" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "workOrderId": 9001,
    "scope": "Replace condenser fan motor and recharge refrigerant.",
    "laborLineItems": [ { "description": "2 techs x 3 hrs", "amount": "540.00" } ],
    "laborTotalBeforeTax": "540.00",
    "materialLineItems": [ { "description": "Fan motor", "amount": "310.00" } ],
    "materialTotalBeforeTax": "310.00",
    "totalBeforeTax": "850.00",
    "taxRate": "8.5",
    "tax": "72.25",
    "totalAfterTax": "922.25"
  }'
```

Beteende att känna till:

- `locationId`, `buyerFacilityId` och `buyerCompanyId` härleds från arbetsordern; du kan inte sätta dem.
- Osatta skattefält och sektionstotaler blir som standard `"0"`.
- `requestForProposalId` blir som standard arbetsorderns RFP när det utelämnas.
- `proposalPdfLink`, om skickad, måste vara en giltig URL. `attachments` tar `FileDetails` från [filuppladdningsslutpunkten](/sv/supplier-api/files-and-users).
- Att skicka ett `id` uppdaterar ett befintligt förslag.

Följ utfallet genom att hämta om: `status` går från `pending` till `awarded` eller `declined` (avslagsskäl visas i `declineNotes`). Lista med `GET /v1/supplier/quote/proposals` (se [filtrera listor](#filtrera-listor)), läs en med `GET /v1/supplier/quote/proposals/{id}`.

## Fakturor

### Livscykeln

Fakturor börjar som **`draft`** (osynliga för köparen), **publiceras** in i `pending`, sedan flyttar köparen dem genom `approved` och `processing` till `paid` (eller bestrider dem). Din integration skapar utkastet och publicerar det; från `pending` och framåt läser du mestadels status.

### Skapa utkastet

`POST /v1/supplier/invoice/invoices` kräver `workOrderId`; `locationId`, `buyerFacilityId`, `buyerCompanyId`, `spendCategoryId` och `problemTypeId` härleds alla från det.

```bash
curl -X POST "$BASE/v1/supplier/invoice/invoices" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "workOrderId": 9001,
    "invoiceNumber": "INV-2026-0451",
    "dateOfInvoice": "2026-08-21T00:00:00.000-07:00",
    "laborLineItems": [ { "description": "2 techs x 3 hrs", "amount": "540.00" } ],
    "laborTotalBeforeTax": "540.00",
    "materialLineItems": [ { "description": "Fan motor", "amount": "310.00" } ],
    "materialTotalBeforeTax": "310.00",
    "invoiceTotalBeforeTax": "850.00",
    "invoiceTaxRate": "8.5",
    "invoiceTax": "72.25",
    "invoiceTotalAfterTax": "922.25"
  }'
```

Beteende att känna till:

- `poNumber` blir som standard arbetsorderns PO-nummer.
- `serviceCallIds` blir som standard **alla** servicebesök på arbetsordern när det utelämnas eller är tomt; sätt det uttryckligen när du fakturerar en delmängd av besök.
- OpenWrench validerar `taxLineItems` mot fakturavalutans tillåtna skattetyper och avvisar allt annat. För närvarande stödjer endast CAD dem (GST/HST/PST).
- `invoicePDFLink` (en giltig URL) blir fakturans enda PDF-post om du är värd för PDF:en själv; de flesta integrationer använder uppladdningsslutpunkten nedan istället.
- `autoPublishOnApproval` väljer denna faktura för auto-publicering när arbetsordern avslutas.
- Att spara en faktura kan flytta den associerade arbetsorderns status enligt mappningen faktura-till-arbetsorder-status. Ett spar-nivåvalideringsfel returnerar `406`.
- Att skicka ett `id` uppdaterar en befintlig faktura (i praktiken endast utkast; köpar-sidans statusar är inte dina att redigera).

### Ladda upp PDF:en och publicera

`POST /v1/supplier/invoice/file/upload_and_publish/{invoiceId}` gör båda stegen på en gång: den uppladdade PDF:en (multipart-del `file`, max 512 MB) blir fakturans enda PDF, och statusen flyttas till `pending`.

```bash
curl -X POST "$BASE/v1/supplier/invoice/file/upload_and_publish/7710" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  -F "file=@INV-2026-0451.pdf"
```

Slutpunkten returnerar `400` om någon förutsättning misslyckas: din anläggning måste äga fakturan, den associerade arbetsordern måste vara i visningsstatus **Completed**, och köparens konfiguration måste tillåta leverantörsfakturaredigering.

### Läsa och stämma av

`GET /v1/supplier/invoice/invoices` (filtrerbar, se [filtrera listor](#filtrera-listor)) och `GET /v1/supplier/invoice/invoices/{id}`. Tredjepartsleverantörer ser maskerade poster med köpar-privata fält bortrensade. Polla status för att driva din AR-huvudbok: `approvedAt`, `processedAt` och `markedPaidAt` tidsstämplar köparens framsteg.

## Filtrera listor

`GET /v1/supplier/quote/proposals` och `GET /v1/supplier/invoice/invoices` tar `offset`, `limit` (standard 10, max 25), `sort_by` och `order`, plus filtren nedan. Filter kombineras med AND och kombineras alltid med din nyckels tenant-avgränsning, så du ser bara din anläggnings förslag och fakturor. Ingen av listorna har en räkningsslutpunkt; svarets `count` är det totala antalet träffar.

```bash
# Godkända och behandlade fakturor för en köpare, markerade som betalda i augusti
curl -G "$BASE/v1/supplier/invoice/invoices" \
  -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  --data-urlencode "statuses=approved,processing,paid" \
  --data-urlencode "buyerCompanyId=42" \
  --data-urlencode "markedPaidAtStartDate=08/01/2026 00:00:00" \
  --data-urlencode "markedPaidAtEndDate=08/31/2026 00:00:00" \
  -d limit=25 -d sort_by=createdAt -d order=desc

# Väntande förslag på en arbetsorder
curl -H "X-API-KEY: $KEY" -H "OW-KEY: $SECRET" \
  "$BASE/v1/supplier/quote/proposals?status=pending&workOrderId=9001"
```

**Båda listorna**

| Filter | Matchar |
| --- | --- |
| `status`, `statuses` | Statusen, med gemener. Förslag: `draft`, `pending`, `awarded`, `declined`. Fakturor: `draft`, `pending`, `approved`, `processing`, `paid`, `disputed`, `pastdue`, `transferred`, `void`. |
| `workOrderId` | Poster för en arbetsorder. |
| `buyerCompanyId` | Poster för en av dina köparkunder. Det smalnar av dina resultat; det kan inte vidga dem. |
| `locationId`, `locationIds` | Poster för dessa platser. |
| `regionIds` | Poster för platser i dessa regioner. |
| `problemTypeIds` | Poster vars arbetsorder har dessa problemtyper. |
| `woPriorityIds` | Poster vars arbetsorder har dessa prioriteter. |
| `isCapex` | `true` returnerar endast poster för arbetsordrar flaggade som investeringsutgift (capex); `false` utesluter dem. |
| `createdAtStartDate`, `createdAtEndDate` | Poster skapade inom fönstret. |
| `approvedAtStartDate`, `approvedAtEndDate` | Förslag tilldelade, eller fakturor godkända, inom fönstret. |
| `workCompletedAtStartDate`, `workCompletedAtEndDate` | Poster vars arbetsorder slutfördes inom fönstret. |

**Endast förslag**

| Filter | Matchar |
| --- | --- |
| `search` | En del av arbetsorderns titel. Ett numeriskt värde matchar också förslagets id eller arbetsorderns id exakt. |

**Endast fakturor**

| Filter | Matchar |
| --- | --- |
| `search` | En del av arbetsorderns titel, eller exakt ett av: arbetsorder-id, externt arbetsorder-id, fakturanummer, faktura-id, PO-nummer, GL-kod. |
| `invoiceNumber` | Fakturor med detta fakturanummer. |
| `externalWorkOrderId` | Fakturor för en arbetsorder, via köparens externa referens på den. |
| `workOrderDisplayStatus` | Fakturor vars arbetsorder har denna visningsstatus: `Pending`, `Deferred`, `Open`, `InProgress`, `OnHold`, `Completed` eller `Cancelled`. |
| `assetId`, `assetIds` | Fakturor vars arbetsorder gäller dessa tillgångar. |
| `problemTypeId` | Fakturor vars arbetsorder har denna problemtyp. |
| `isPM` | `true` returnerar endast fakturor för arbetsordrar för förebyggande underhåll; `false` utesluter dem. |
| `publishedAtStartDate`, `publishedAtEndDate` | Fakturor publicerade till köparen inom fönstret. |
| `processedAtStartDate`, `processedAtEndDate` | Fakturor som köparen flyttade till `processing` inom fönstret. |
| `markedPaidAtStartDate`, `markedPaidAtEndDate` | Fakturor markerade som betalda inom fönstret. Användbart för AR-avstämning. |
| `dueAtStartDate`, `dueAtEndDate` | Fakturor som förfaller inom fönstret. |

Regler för filtervärden:

- **Sortering.** Båda listorna sorterar efter `createdAt`, `id`, `workOrderId`, `locationId`, `supplierFacilityId` eller `buyerFacilityId`; fakturor sorterar även efter `invoiceTotalAfterTax`, och förslag efter `updatedAt` och `totalAfterTax`. När du sätter `sort_by` blir `order` som standard `asc`, så skicka `order=desc` för nyast först. Utan `sort_by` kommer fakturor nyast först och förslag i `id`-ordning (äldst först). Ett `sort_by` som inte stöds på förslag faller också tillbaka på `id`-ordning.
- **Listor tar kommatecken utan mellanslag.** En nyckel i singular (`status`) tar ett värde; nyckeln i plural tar en kommaseparerad lista. `status=pending,approved` letar efter en enda status med just det namnet och returnerar ingenting. Ett mellanslag efter ett kommatecken kan få anropet att misslyckas.
- **Ett värde per nyckel.** Om du upprepar en parameter används bara den första.
- **Datum använder `MM/dd/yyyy HH:mm:ss` i UTC**, till exempel `08/01/2026 00:00:00`. Tiden är obligatorisk. Startgränsen är inkluderande från den tid du skickar; slutgränsen täcker hela slutdagen (dess tid ersätts med 23:59:59). URL-koda värdet. Ett datum som inte kan tolkas läses som 1 januari 1970 istället för att avvisas, så ett felaktigt startdatum matchar allt och ett felaktigt slutdatum matchar ingenting.
- **Värden måste vara välformade.** Ett icke-numeriskt id, eller ett booleskt värde annat än `true` eller `false`, kan få anropet att misslyckas med `500` istället för `400`.
- **Okända filter ignoreras**, och din tenant-avgränsning kan inte åsidosättas: `supplierFacilityId` sätts alltid från din API-nyckel.

## End-to-end-faktureringsflöde

1. Arbetsordern når offereringsfasen: skicka in ett förslag, vänta på `awarded`.
2. Slutför arbetet via [utcheckning från servicebesök](/sv/supplier-api/service-calls#3-checka-ut-och-sätt-utfallet).
3. Skapa fakturautkastet; generera din PDF.
4. När arbetsordern visar Completed, `upload_and_publish`.
5. Polla fakturastatus tills `paid` och stäm av mot `markedPaidAt`.
